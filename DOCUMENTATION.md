# Как это устроено

Справочник по архитектуре: модель доступа, изоляция, лимиты, авторизация, бэкап,
мониторинг. Если нужно **развернуть** сервер — идите в [DEPLOYMENT.md](DEPLOYMENT.md),
этот файл объясняет, почему всё сделано именно так.

---

## 1. Что это даёт

- Единая среда разработки на сервере — не зависит от локального железа.
- Каждый сотрудник изолирован и не видит чужие файлы.
- Работа лежит в одном месте: бэкапится, учитывается, не разъезжается по ноутбукам.
- Полный стек из коробки: Node, PHP, Python, Docker, Composer, PHPUnit, PHPStan.

**Профиль машины.** Рецепт рассчитан на сервер под интерактивную работу команды и
лёгкие веб-сервисы. Ориентир — от 2 ГБ RAM на человека плюс запас; на четырёх ядрах
и 8 ГБ комфортно работают 6–8 человек. Это **не** билд-ферма: тяжёлые нативные
сборки (Android/NDK, крупные C++-проекты) одного человека способны положить
интерактивность всем — их место на отдельной машине или локальной станции.

## 2. Модель доступа

| Роль | Права |
|---|---|
| `root` | вход по ключу, `prohibit-password` |
| эталонный пользователь (`coder`) | sudo + системный docker; при общем аккаунте — **источник токена** |
| администратор | sudo NOPASSWD, системный docker, вход под root |
| разработчик | изолирован, без sudo, rootless docker |

Вход **только по SSH-ключу**, парольная аутентификация отключена.

### Изоляция

- **Домашние папки `750`** (`drwxr-x---`, владелец:своя группа) — обычные
  пользователи не видят файлы друг друга. Проверяется под uid:
  `sudo -u <кто-то> ls /home/<другой>` → `permission denied`.
- **Ни sudo, ни группы `docker`** у разработчиков. Обе привилегии эквивалентны
  root: имея docker, можно смонтировать чужой `/home` в контейнер и прочитать всё.
  Поэтому обычным пользователям — rootless Docker (§4).
- **`/tmp` общий и виден всем** (штатный режим `1777`). Это не чинится правами
  на каталог — только `UMASK` в `/etc/login.defs`.

### Гранула: `UMASK 027` и почему не жёстче

По умолчанию (`UMASK 022` + `USERGROUPS_ENAB yes`) файлы в общем `/tmp` создаются
мирочитаемыми, и содержимое чужих файлов доступно всем. `UMASK 027` даёт
эффективный `0007` у пользователей и `0027` у root — новые файлы получают
`-rw-rw----` и чужим не читаются.

⚠️ **Жёстче брать нельзя, если вы используете ACL.** Маска ACL берётся из
group-битов режима создания: `umask 077` обнулит их и молча схлопнет
`user:X:rwx` в `#effective:---` на всех новых файлах. В каталогах с default-ACL
umask вообще игнорируется — там права диктует ACL.

⚠️ **Фикс покрывает только новые PAM-сессии.** При `linger=yes` (нужен для
rootless Docker) `systemd --user` поднимается при загрузке **вне** PAM и держит
старый umask до перезапуска пользовательского менеджера или сервера. Полное
применение требует либо `UMask=` в drop-in для `user@.service`, либо
`systemctl restart user@<uid>.service` (**убьёт живые сессии, включая
VSCode-сервер**), либо перезагрузки.

⛔ **Приватный `/tmp` через `pam_namespace`** выглядит привлекательно, но плохо
сочетается с `linger`: пользовательские юниты, поднятые вне PAM-сессии, увидят
настоящий `/tmp`, а ssh-сессия — приватный. Один человек, два разных `/tmp`.
Плюс любые скрипты с зашитыми путями `/tmp` ломаются. Альтернатива попроще —
`TMPDIR=$HOME/.tmp` через `pam_env`, но она мимо тех же хардкодов.

### Что песочница агента не делает

**Песочница ограничивает запись, а не чтение.** Во всех режимах агент читает
всё, куда пускает ОС: имена папок в `/home` (режим `755`), корневые `/etc`,
`/var`, `/opt`, `/usr`. Штатный режим — `workspace-write`; если рабочие сценарии
требуют сети и доступа ко всему дому, это добавляется явно
(`network_access=true`, `writable_roots=["/home/<логин>"]`), а не переводом в
режим полного доступа.

Видимость чужих папок определяется правами ОС, а не настройками песочницы — не
путайте эти два слоя при разборе жалоб «я стал видеть больше».

### Привилегии разработчика без админа

Всё ставится в свой профиль, без sudo:

- PHP — `composer require --dev …` или `composer global require …`
- Python — `python3 -m venv .venv && pip install …`
- Node — `npm install -g …` уходит в `~/.npm-global` (префикс в `~/.npmrc`)
- PATH (`~/.local/bin`, `~/.npm-global/bin`, composer global bin) — в `~/.bashrc`

Админ нужен только для системных пакетов (`apt`).

## 3. Авторизация агента

Скрипт `codex-add-user.sh` и вся инфраструктура работают одинаково при любом
способе входа. Разница только в том, нужны ли скрипты раздачи токена.

**Персональная авторизация (рекомендуется).** Каждый логинится сам — своей
учёткой или своим API-ключом. Раздавать нечего: `codex-auth-sync.sh`,
`codex-reauth.sh` и `codex-token-expiry-warn.sh` не нужны, не ставьте их и
не заводите соответствующие cron-задачи. Расход, ротация и блокировка одного
человека не задевают остальных. Дашборд расхода (§6) при этом работает
без изменений — он читает файлы сессий и к способу входа безразличен.

**Общий аккаунт на команду** (см. «Ограничения» в README). Подписка одна на всех,
поэтому нужен обходной механизм:

- Режим `auth_mode=chatgpt`, файл `~/.codex/auth.json` у каждого.
- access-токен живёт порядка недели-полутора, затем обновляется по refresh.
- **Проблема:** при ротации refresh-токена успешно обновится только тот, кто
  успел первым; остальных выбьет. Сотрудники переавторизоваться сами не могут —
  нужен пароль от общего аккаунта.
- **Обход:** cron каждые 6 часов запускает `codex-auth-sync.sh`, который
  обновляет токен **только у эталонного пользователя** и раскладывает свежий
  `auth.json` остальным. Никто не рефрешит самостоятельно — никого не выбивает.

⚠️ Если разлогинило всех, простой `codex login --device-auth` может не
удержаться: фоновые `codex app-server` со старым отозванным токеном ре-убивают
свежий логин. Для этого есть `codex-reauth.sh` — он снимает всех клиентов,
отодвигает старые `auth.json`, логинит заново, проверяет живость реальным
запросом и только потом раздаёт.

⚠️ **Детекция смерти токена должна искать позитивный признак, а не сигнатуры
отказа.** При рассинхроне версии CLI со схемой API клиент способен вывалить в
stderr сотни килобайт служебного текста, внутри которого встречаются фразы вроде
`already used` — и грубый греп примет живой токен за мёртвый. Опаснее всего то,
что при этом **молча останавливается раздача**, и команда постепенно остаётся с
протухшими копиями. Проба просит агента ответить `PONG`; сигнатуры отказа
проверяются вторым шагом и только в очищенном выводе.

### Блокировка доступа отдельному пользователю

Забрать доступ к агенту у одного человека, не трогая остальных, при общем
аккаунте нетривиально — файл можно вернуть, а крон его и вернёт. Работает
только комбинация из четырёх слоёв, и она реализована в
[`codex-auth-exclude.conf`](server-scripts/codex-auth-exclude.conf) и
[`codex-block-watch.sh`](server-scripts/codex-block-watch.sh) — там же рецепт
целиком, включая рабочие грабли с правами на каталог.

При персональной авторизации всё это не нужно: доступ отзывается на стороне
провайдера.

## 4. Rootless Docker

- У каждого изолированного пользователя **свой** движок, поднятый через
  `systemd --user` с `linger=yes` — живёт без активной сессии и переживает
  перезагрузку.
- Сокет `unix:///run/user/<UID>/docker.sock`, `DOCKER_HOST` прописан в `~/.bashrc`.
- Контейнеры работают от имени пользователя и не могут добраться до чужих файлов.
- Ограничение: нельзя слушать порты < 1024.

## 5. Лимиты ресурсов

Без лимитов один тяжёлый процесс выедает память машины, и глобальный OOM-killer
убивает процессы **посторонних** пользователей — их контейнеры, базы, сессии.
Задача лимитов — удержать радиус ущерба внутри того, кто его создал.

Файлы: `/etc/systemd/system/user-.slice.d/` (root исключается одноимёнными
файлами в `user-0.slice.d/`), копии — в `server-scripts/`.

| Параметр | Роль |
|---|---|
| `MemoryHigh` | мягкий тормоз: реклейм и вытеснение в swap, без убийства |
| `MemoryMax` | жёсткий потолок: OOM-killer работает внутри cgroup виновника |
| `MemorySwapMax` | **обязателен** вместе с двумя предыдущими |
| `CPUQuota` | потолок процессорного времени |

**Почему `MemorySwapMax` обязателен.** Лимит RAM не убивает процесс, а выдавливает
его страницы в **общий** swap. Без лимита свопа один пользователь занимает весь
swap машины, и она уходит в thrash — высокий load, всё в D-state — при нулевом
счётчике OOM. Симптом выглядит как «сервер упал», хотя ничего не падало.

**Третий сценарий, который не закрывают оба лимита.** Слайс, упёршийся
одновременно в `MemoryHigh` и `MemorySwapMax`, сбрасывать страницы больше некуда,
и каждое выделение памяти уходит в прямой реклейм. Получается высокий load при
простаивающем CPU и большом проценте системного времени. Клетка ограничивает
ущерб, но не мешает виновнику душить машину через sys-время — поэтому нужен ещё
и `CPUQuota`, и мониторинг нагрузки (§6).

⚠️ **Проверять применение только через `systemctl show`**, а не по факту записи
файла:

```bash
systemctl show user-<uid>.slice -p CPUQuotaPerSecUSec -p MemorySwapMax -p MemoryMax
```

Невалидное значение (классика — `CPUQuota=250%%` с двойным процентом) systemd
принимает молча: файл на месте, лимита нет.

**Как подбирать числа.** Снимите `memory.peak` со слайсов за неделю нормальной
работы и берите потолок с запасом над легитимным пиком. Взятые «на глаз» низкие
лимиты душат обычную работу и вы их снимете через день.

Откат: `rm -rf /etc/systemd/system/user-.slice.d /etc/systemd/system/user-0.slice.d && systemctl daemon-reload`

## 6. Что работает автоматически

| Скрипт | Что делает |
|---|---|
| `codex-add-user.sh <логин> [admin]` | завести сотрудника одной командой |
| `codex-backup.sh [prune]` | бэкап в S3 через restic (cron) — §6.1 |
| `codex-monitor.sh [daily]` | мониторинг + алерты в Telegram (cron) — §6.2 |
| `codex-autoreboot.sh` | умная перезагрузка после обновлений — §6.3 |
| `codex-hungjob-reaper.sh` | снимает зависшие браузерные джобы (cron) — §6.4 |
| `codex-docker-prune.sh` | еженедельная чистка docker (системный + rootless) |
| `codex-usage-*.py/sh` | веб-дашборд расхода — §6.5 |
| `tg-send.sh "текст"` | отправка сообщения в Telegram |
| `codex-auth-sync.sh`, `codex-reauth.sh`, `codex-token-expiry-warn.sh` | **только для общего аккаунта** (§3) |
| `codex-block-watch.sh` | принудительная блокировка доступа (§3) |

### 6.1. Бэкап и восстановление (restic → S3)

- **restic**: шифрование, дедупликация, инкрементальные копии.
- Любое S3-совместимое хранилище. Бакет — **приватный**; «холодный» класс
  дешевле и для ночных бэкапов подходит.
- Конфиг (ключи S3 + пароль шифрования) — `/etc/restic/env`, root, `600`.
- Исключения — `/etc/restic/excludes.txt` (`node_modules`, `vendor`, `.venv` …).
- Расписание: ночной бэкап, `prune` раз в неделю.
- Хранение: 14 дневных / 8 недельных / 6 месячных снимков.

⚠️ **Пароль шифрования храните отдельно от сервера** (менеджер паролей). Без него
копии не восстановить — это не «можно будет подобрать», а буквально не восстановить.

⚠️ **`--group-by host` в `forget` обязателен.** Иначе снимки группируются по набору
путей, и при добавлении нового пользователя состав группы меняется — старые снимки
перестают подчищаться и репозиторий растёт бесконечно.

```bash
source /etc/restic/env
restic snapshots                        # список копий
restic restore latest --target /tmp/r   # восстановить всё
restic restore latest --target /tmp/r --include /home/<логин>/projects/<проект>
restic stats                            # размер репозитория
```

**Демо-восстановление стоит прогнать сразу после настройки.** Бэкап, который
никто ни разу не разворачивал, — это не бэкап, а надежда.

### 6.2. Мониторинг и алерты

Ежечасная проверка плюс суточная сводка в Telegram (токен и chat_id —
`/etc/telegram/env`, root, `600`).

Проверяется: заполнение диска, диск по пользователям, размер `/tmp`, свежесть
бэкапа, OOM, службы cron/docker, флаг «требуется перезагрузка» и **нагрузка** —
`load1` относительно числа ядер, занятость swap, залипание на IO
(`/proc/pressure/io some avg60`).

Три вещи, без которых монитор бесполезен:

- **Следить не только за диском.** Машина становится полностью недоступной при
  свободном диске — своп-тромб, высокий load, процессы в D-state. Монитор,
  который смотрит только на место, такие эпизоды просто не увидит, и о них вы
  узнаете от сотрудников, а не от автоматики.
- **Алерт должен называть виновника.** Топ считается по
  `memory.current + memory.swap.current` **cgroup-слайса `user-<uid>.slice`** —
  тогда в сообщении стоит имя человека, а не безымянный `java` или `chrome`.
  Алерт «диск 90%» без ответа на вопрос «чей» бесполезен в три часа ночи.
- ⚠️ **Анти-спам ключевать на КЛАСС проблемы, а не на её текст.** Добавляя
  проверку, вызывайте `add_problem КЛЮЧ ТЕКСТ`, где ключ **не содержит живых
  значений**. Иначе меняющаяся цифра («диск 87%» → «90%») даёт новую сигнатуру,
  и алерт летит каждый час вместо раза в 6 часов.

### 6.3. Автообновления и перезагрузка

`unattended-upgrades` ставит security-патчи ночью; встроенная авто-перезагрузка
отключена. `codex-autoreboot.sh` перезагружает машину **только если никто не
работает** — нет SSH-сессий, VSCode и процессов агента. Иначе откладывает на
следующую ночь и сообщает в Telegram; после нескольких откладываний эскалирует.

### 6.4. Жнец зависших джобов

Браузерная автоматика (headless Chrome, Playwright), запущенная агентом, умеет
зависать и удерживать гигабайты памяти неограниченно долго. Две независимые ветки:

- **blocklist** — команды, которым на сервере быть не должно (regex в конфиге);
- **гигиена браузеров** — любой `chrome-headless-shell`/`chromium`/`Xvfb`
  старше порога. Забытые процессы живут неделями и жгут CPU впустую.

Ключевые свойства: снимает **дерево целиком**, включая обёртки песочницы (иначе
`--die-with-parent` не срабатывает); никогда не трогает root, VSCode-сервер и
хост агента; сигнал только `TERM`.

⚠️ **Зависший джоб отличается от работающего не наличием процесса, а
отсутствием прогресса**: смотрите накопленное CPU-время и mtime вывода, а не
факт, что процесс жив и порт занят.

⚠️ **Против агента с авто-ретраем работает только автоматика того же темпа.**
Ручной `kill` бесполезен — агент в открытой сессии перезапустит джоб через
пару минут, и правило, добавленное в его инструкции сейчас, эта сессия не увидит.

### 6.5. Веб-дашборд расхода

Расход по сотрудникам и проектам: Caddy с автоматическим TLS, basic-auth,
логины совпадают с системными. Роли: администратор видит имена и проекты,
сотруднику общий борд **обезличен** (коллеги показаны как «Сотрудник N»).
Есть страница смены собственного пароля и фильтр периодов.

**Это прокси по логам, а не биллинг.** Дашборд считает события и вызовы
инструментов, читая файлы сессий, — сопоставлять его цифры со счётом провайдера
не следует.

**Ledger истории.** Отдельный ежечасный снимок складывает почасовые агрегаты в
собственное хранилище и пишет **только «вверх» (MAX)**. Без него обычная чистка
старых сессий одним человеком обнуляет историю дашборда: пока файл жив — событие
видно, удалили файл — окно «7 дней» показывает один день.

⚠️ **Известное ограничение: проект определяется по рабочему каталогу сессии.**
Если у вас принято запускать агента из общего каталога-хаба, вся работа
запишется на этот хаб, и разбивка по проектам станет бессмысленной. Прежде чем
опираться на цифры, проверьте, как в вашей команде реально запускают агента.

## 7. Подключение из VSCode

1. Локально: расширение **Remote-SSH**, ключ в `~/.ssh`, хост в `~/.ssh/config` —
   всё это делает скрипт из персонального комплекта.
2. `F1` → **Remote-SSH: Connect to Host** → хост сервера.
3. **Open Folder** → `/home/<логин>/projects`.
4. Терминал → `codex`.

Шаблоны комплектов — в [`setup-new-pc/`](setup-new-pc/).

⚠️ Версия VSCode и версия расширения агента живут своей жизнью: панель агента
запускает **свой** бинарь из расширения, а не системный CLI. Обновление
редактора способно сломать панель независимо от того, что стоит на сервере —
при массовом «у всех перестало работать» проверяйте это раньше, чем токен.

## 8. Шпаргалка администратора

```bash
# новый сотрудник
codex-add-user.sh ivan            # обычный
codex-add-user.sh petr admin      # администратор

# заблокировать / разблокировать / удалить
usermod -L ivan ; usermod -U ivan
deluser --remove-home ivan

# состояние
tail /var/log/codex-monitor.log
tail /var/log/codex-backup.log
sudo -u ivan codex login status
```

**Offboarding — полный список**, а не только удаление учётки:

1. `deluser --remove-home <логин>` (или `usermod -L`, если данные ещё нужны);
2. убрать его ключ из `authorized_keys` там, где он мог быть добавлен вручную;
3. убрать веб-логин дашборда (строка в Caddyfile + его каталог);
4. отозвать внешние доступы, которые выдавались персонально;
5. при персональной авторизации — отозвать его ключ или учётку у провайдера;
6. проверить, не осталось ли его данных в общих каталогах (`/tmp`, `/var/tmp`).
