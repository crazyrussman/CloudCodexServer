# CloudCodexServer

Сервер для командной работы с **AI-агентом в терминале** (OpenAI Codex CLI) через
**VSCode Remote-SSH**. Каждый разработчик подключается из своего VSCode и запускает
агента прямо на сервере: код, зависимости, контейнеры и сам агент живут там,
изолированно по пользователям.

Это не библиотека и не приложение, а **воспроизводимый рецепт эксплуатации**:
пошаговый runbook развёртывания, ~20 серверных скриптов и объяснение, почему
каждое решение принято именно таким.

## Зачем это может быть нужно

- Слабые или разнородные ноутбуки, а агенту нужны ресурсы и Linux-окружение.
- Работа должна оставаться в одном месте: бэкапится, учитывается, не разъезжается
  по личным машинам.
- Нужен контроль: кто сколько тратит, кто что запускает, что происходит ночью.

## Что внутри

**Изоляция и лимиты.** Домашние папки `700`, rootless Docker для обычных
пользователей, песочница агента с ограничением записи. На каждого — cgroup-лимиты
`MemoryHigh`/`MemoryMax`/`MemorySwapMax`/`CPUQuota`, чтобы один тяжёлый процесс не
уронил работу остальных.

**Бэкап.** restic → S3: инкрементально, зашифрованно, с ретеншном и еженедельным
`prune`. Бэкапятся проекты, docker-тома, конфиги и накопленная память агента.

**Мониторинг.** Ежечасная проверка и суточная сводка в Telegram: диск, свежесть
бэкапа, OOM, службы и **нагрузка** — load, swap, залипание на IO. В каждом алерте
**имя виновника**, вычисленное по cgroup-слайсу, а не безымянный `chrome`.

**Жнец зависших джобов.** Крон снимает браузерную автоматику, которая зависла и
удерживает память: гигиена по возрасту процесса плюс точечный blocklist. Снимает
дерево целиком, включая обёртки песочницы; никогда не трогает root, VSCode-сервер
и хост агента.

**Веб-дашборд расхода.** Кто сколько потребляет, с разбивкой по проектам, за Caddy
с TLS и basic-auth. Администратор видит имена, сотруднику общий борд обезличен.
История ведётся в отдельном ledger'е, поэтому чистка сессий её не стирает.

**Обслуживание.** Автообновления безопасности и умная перезагрузка — только когда
никто не работает.

## Быстрый старт

```bash
# 1. Развернуть сервер — по шагам из DEPLOYMENT.md (Ubuntu 24.04)

# 2. Завести сотрудника
codex-add-user.sh ivan          # обычный, изолированный
codex-add-user.sh petr admin    # второй администратор

# 3. Собрать ему комплект подключения из setup-new-pc/_templates/
```

Скрипт заводит учётку, настраивает изоляцию и rootless Docker и печатает приватный
ключ для передачи сотруднику.

## Авторизация: два варианта

Инфраструктура одинакова в обоих случаях, различается только набор скриптов.

**Персональная авторизация — рекомендуемый путь.** Каждый входит своей учёткой или
своим API-ключом. Скрипты раздачи и восстановления токена (`codex-auth-sync.sh`,
`codex-reauth.sh`, `codex-token-expiry-warn.sh`) при этом **не нужны** — просто не
ставьте их. Расход, ротация и отзыв доступа у одного человека не задевают
остальных. Дашборд расхода работает без изменений.

**Общий аккаунт на команду** — так это работало у нас, и код для такой схемы в
репозитории есть. Прежде чем её выбирать, прочитайте следующий раздел.

## Ограничения — прочитайте до внедрения

Схема с общим аккаунтом провайдера опубликована как есть, но у неё высокая цена:

- **Это, по всей вероятности, нарушает условия использования провайдера.**
  Никаких гарантий: аккаунт может быть заблокирован в любой момент вместе с
  работой всей команды. Решение и ответственность — ваши.
- **Общий лимит.** Один человек способен выжечь недельную квоту команды за сутки,
  и остальные узнают об этом, когда работа встанет.
- **Общая смерть токена.** Отзыв или истечение токена останавливает всех сразу;
  до ручного восстановления команда простаивает.
- **Веб-вход извне убивает сессию.** Логин в тот же аккаунт из браузера с другого
  IP отзывает токен у всей команды.

Персональные учётки или API-ключи снимают все четыре пункта разом. Скрипты
`codex-auth-sync.sh`, `codex-reauth.sh`, `codex-token-expiry-warn.sh` и
`codex-block-watch.sh` существуют **только** для обслуживания общей схемы.

**Прочее.** Проверялось на Ubuntu 24.04. Профиль машины — интерактивная работа
команды и лёгкие веб-сервисы, а не билд-ферма: тяжёлые нативные сборки одного
человека способны положить интерактивность всем. Все примеры обезличены —
`<SERVER_IP>`, `codex.example.com`, логины `ivan`/`petr`; подставьте свои.

## Секреты

В репозитории **нет и не должно быть** приватных ключей, паролей и токенов.
На сервере они лежат так:

| Где | Что |
|---|---|
| `/etc/restic/env` | ключи S3 и пароль шифрования бэкапа |
| `/etc/telegram/env` | токен бота и chat_id для алертов |
| `/root/codex-usage-credentials.txt` | пароли логинов дашборда |
| `/etc/codex-usage-account.env` | токен сервиса смены паролей |

Пароль шифрования restic храните отдельно от сервера — без него копии не
восстановить.
